# AGENTS.md — рабочие правила репозитория

Эти правила обязательны для Codex и других агентов, работающих в этом репозитории.

## Перед правками

1. Сначала изучить структуру проекта:
   - `CLAUDE.md`;
   - `texts/README.md`;
   - `texts/NEXT.md`;
   - профильные `README`;
   - package/config-файлы, если есть;
   - деплой, PWA/service worker, базу данных, env-пример, если они есть;
   - текущий `git status --short --branch`.
2. Не вносить самодеятельность: не менять дизайн, картинки, тексты, архитектуру и сторонние файлы без прямой причины.
3. Если задача узкая, править только нужные места.
4. Перед рискованными изменениями делать backup или отдельную ветку.
5. Не использовать `git reset --hard`, `git checkout --`, удаление файлов и другие разрушительные команды без явного разрешения.

## Данные и база

1. Не ломать данные.
2. Если клиентский код зависит от новой колонки, таблицы или переменной, сначала добавить миграцию или SQL-инструкцию, затем fallback в коде.
3. Никогда не выкатывать schema-dependent клиент без проверки базы.
4. Секреты и API-ключи не вставлять в клиентский код и не коммитить.
5. Использовать `.env`, secrets платформы деплоя или backend/edge-функции.

## PWA и web

1. После frontend-правок обновлять версию сборки/cache/service worker, если проект использует PWA/cache.
2. Проверять, что `index.html`, основной JS/CSS и `sw.js` не рассинхронизированы.
3. Если проект имеет beta-версию, поддерживать явную версию: `APP_VERSION`, `CACHE_VERSION`, changelog или beta label.
4. После заметных изменений обновлять номер или метку версии.

## Git

1. После завершения задачи проверить `git status`.
2. Добавлять только связанные с задачей файлы.
3. Не использовать слепой `git add -A`.
4. Делать короткий понятный commit.
5. Push в текущую ветку делать только если это безопасно и пользователь не запретил.
6. Если в дереве есть несвязанные изменения, не включать их в commit и явно упомянуть в финальном ответе.

## Деплой и CI

1. Не ждать деплой бесконечно.
2. После push проверить стартовый статус деплоя/CI, если он есть.
3. Если процесс долгий, дать ссылку/статус и продолжать без многочасового ожидания.

## Финальный ответ

В конце всегда коротко писать:

- что изменено;
- что проверено;
- был ли commit/push;
- что осталось сделать, если есть.
